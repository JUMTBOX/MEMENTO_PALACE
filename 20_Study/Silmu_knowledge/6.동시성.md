## 6. 동시성, 데이터가 꼬이기 전에 잡아야 한다

**서버와 동시 실행**
- 서버가 동시에 여러 클라이언트의 요청을 처리하는 방식 2가지
  - `클라이언트 요청마다 스레드 할당하여 처리`  ex. Spring
  - `비동기 I/O(또는 non-blocking I/O)를 사용해서 처리`  ex. express.js, Nest.js

**동시성 제어(`Java 구현체`)**
- Lock (`ReentrantLock, synchronized`)
- Semaphore (`Semaphore`)
  - 동시에 실행할 수 있는 스레드 수를 제한, 자원에 대한 접근을 일정 수준으로 제한하고 싶을 때 사용 할 수 있음
  - ```text
    1. 세마포어에서 permit 획득 (허용 가능 숫자 1 감소)
    2. 코드 실행
    3. 세마포어에 permit 반환 (허용 가능 숫자 1 증가)
    ```
- 읽기/쓰기 잠금(`ReadWriteLock, ReentrantReadWriteLock`)
  - ```text
    [읽기/쓰기 잠금의 특징]
    - 쓰기 잠금은 한 번에 한 스레드만 구할 수 있다.
    - 읽기 잠금은 한 번에 여러 스레드가 구할 수 있다.
    - 한 스레드가 쓰기 잠금을 획득했다면 쓰기 잠금이 해제될 때까지 읽기 잠금을 구할 수 없다.
    - 읽기 잠금을 획득한 모든 스레드가 읽기 잠금을 해체할 때까지 쓰기 잠금을 구할 수 없다.
    ```

**동시성 지원 컬렉션**
- `Collections`은 동기화된 컬렉션을 생성하는 메서드를 제공, 기존 컬렉션 객체를 쉽게 동기화된 컬렉션 객체로 변경 가능
```java
Map<String, String> map = new HashMap<>();
/*  동기화된 컬렉션 객체 생성 */
Map<String, String> syncMap = Collections.synchronizedMap(map);
syncMap.put("key1", "value1");  /* put 메서드는 내부적으로 synchronized 처리 */
```
```text
JDK 23 또는 이전 버전 기준으로 가상 스레드를 사용한다면 Collections.synchronizedMap(...)을 포함한
동기화 컬렉션 객체 변환 메서드를 사용하면 안 된다. 내부적으로 synchronized를 사용하여 동시 접근을 
동기화 하기 때문이다.
JDK 23 또는 이전 버전 기준으로 가상 스레드는 아직 synchronized를 지원하지 않기에 성능에 문제가 발생할 수 있다.
```

**DB와 동시성**
- Pessimistic Lock(비관적/선점적 락) : `@Lock(LockModeType.PESSIMISTIC_WRITE), @Lock(LockModeType.PESSIMISTIC_READ)`
  - 간단한 분산 락(distributed lock) 구현 시 DBMS에서 제공하는 Pessimistic lock을 사용해 구현 가능
  - Redis 기반 분산 락 구현 방안도 존재
- Optimistic Lock (낙관적/비선점 락) : `@Lock(LockModeType.OPTIMISTIC), @Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)`
  - JPA Entity에 `@Version`이 달려있는 필드가 존재하면 Hibernate가 일반적으로 `[수정]` 시 다음과 같은 `UPDATE` 쿼리 실행
  - ```java
    @Transactional
    public void decreaseStock(Long couponId) {
      Coupon coupon = couponRepository.findById(couponId).orElseThrow();
      
      coupon.decreaseStock();
    }
    ```
  - ```sql
    UPDATE coupon
    SET remaining_stock = 99,
        version = 6
    WHERE id = 1
      AND version = 5;
    ```
  - 즉, `LockModeType.OPTIMISTIC`을 지정하지 않아도 기본적인 낙관적 락 검증이 작동 
  - 따라서 `LockModeType.OPTIMISTIC`을 명시적으로 사용하는 경우는 
  > Entity를 변경하지 않더라도, 읽은 시점부터 트랜잭션 종료까지 해당 버전이 유지되었는지 보장하고 싶을 때
  
**외부 연동과 잠금**
- 트랜잭션 범위 내에서 외부 시스템과 연동해야 한다면, 비선점 잠금보다는 선점 잠금을 고려하는 것이 좋다
- 비선점 잠금을 사용하고 싶다면 `트랜잭션 아웃박스 패턴`을 적용하여 처리 가능

**증분 쿼리**
```sql
UPDATE subject SET join_count = join_count + 1 WHERE id = ?;
```
- DB는 `join_count = join_count + 1`을 원자적 연산으로 처리한다.
  - 사용1: `@Query("UPDATE... SET ... WHERE")` 어노테이션 사용한 메서드 정의
  - 사용2: QueryDSL 사용 <br/>
    ```java
      public void incrementViewsWithQDSL(Long id_p) {
        queryFactory.update(product)
          .set(product.views, product.views.add(1))
          .where(product.id.eq(id_p))
          .execute();
      }
    ```
**주의 사항**
- 잠금 해제하기
- 대기 시간 지정하기
- 교착 상태(deadlock) 피하기
