## 5. 비동기 연동

**🔑비동기 연동의 5가지 처리 방식**
1. 별도 스레드로 실행하기
    - `new Thread`,`Executors.newFixedThreadPool`,`@Async`, 
2. 메시징 시스템 사용하기
   - `kafka`
     - 높은 처리량 (1,000,000 TPS)
     - 수평 확장 용이
     - 메시지를 파일(disk?)에 저장하기 때문에 메시지가 유실되지 않음
     - 1개의 topic이 여러 파티션을 가질 수 있는데, 파티션 단위로 순서를 보장함. 하지만 topic 수준에서는 순서 보장 안됨
     - consumer는 메시지를 언제든지 재처리할 수 있음
     - 풀(pull) 모델을 사용함, consumer가 kafka 브로커에서 메시지를 읽어 가는 방식
   - `RabbitMQ`
     - 클러스터링을 통해 처리량을 높일 수 있지만, kafka 보다 더 많은 리소스를 필요로 함
     - 메모리에만 메시지를 보관하는 큐 설정을 사용하면 장애시 메시지가 유실될 가능성 존재
     - 메시지는 큐에 등록된 순서대로 consumer에 전송
     - 메시지가 consumer에 전달됐는지 확인하는 기능 제공
     - Push 모델을 사용함, RabbitMQ 브로커가 consumer에게 메시지를 전송, consumer 성능이 느려지면 큐에 과부하가 걸려 전반적인 성능 저하 발생 가능성 존재
     - 다재다능함, AMQP, STOMP 등 여러 프로토콜을 지원하고, Pub/Sub 패턴뿐만 아니라 Request/Respons, Point-to-Point 패턴도 지원함, 또한 우선순위를 지정해서 처리 순서를 변경할 수도 있음
   - `Redis Pub/Sub`
     - 메모리 사용으로 지연 시간이 짧고, RabbitMQ 대비 처리량이 높음
     - Subscriber가 없으면 메시지 유실
     - 기본적으로 영구 메시지를 지원하지 않음
     - 모델이 단순하여 사용하기 쉬움 , 적은 장비로도 높은 성능을 낼 수 있다.
   - **Producer(생산자) 측 고려 사항**
     - `메시지 유실에 대한 고려`
       1. 무시
       2. 재시도
       3. 실패 로그 남기기
     - `DB 트랜잭션과의 연동 고려`
       - `글로벌 트랜잭션(global transaction)?`
         - 여러 DB에 대한 변경을 한 트랜잭션으로 묶어서 처리할 수 있다.
         - 구현 알고리즘으로는 2PC(2-Phase Commit)을 사용 (ActiveMQ는 글로벌 트랜잭션 지원)
   - **Consumer(소비자) 측 고려 사항**
     - `메시지 중복 처리에 대한 고려`
       1. Producer가 메시지마다 고유 ID 부여 
       2. 멱등성을 가지도록 API 구현
     - `메시지 소비 현황 모니터링`
   - **메시지 종류: 이벤트 & 커맨드**
     - `이벤트(event)`: 어떠한 일이 발생했음을 알려주는 메시지, 상태(데이터) 변경과 관련 있다.
     - `커맨트(command)`: 무언가를 요청하는 메시지, 커맨드 메시지를 수신하는 소비자(consumer)는 메시지로 요구 받은 기능을 실행

3. 트랜잭션 아웃박스 패턴 사용하기
  - 메시지 데이터 자체가 유실되지 않도록 보장하는 방법은 먼저 해당 데이터를 DB에 저장해두고, 저장된 메시지를 읽어 메시징 시스템에 전송 
  - 메시지 데이터를 DB에 보관하는 방식이 `트랜잭션 아웃박스 패턴(Transaction Outbox Pattern)`의 핵심
  - ```text
    [ process ]
    1. 트랜잭션 시작
    2. 데이터 변경(업무 로직의 DB 작업)
    3. 아웃박스 테이블에 메시지 데이터 저장
    4. 트랜잭션 커밋 
    5. 메시지 중계 프로세스가 아웃박스 테이블에서 메시지 조회
    6. 조회된 메시지 전송
    7. 아웃박스 테이블의 메시지 레코드에 전송 완료 표기  
    ```
  - 트랜잭션이 롤백 된다면 아웃박스 테이블의 메시지 데이터도 롤백되므로 잘못된 메시지 데이터가 전송 될 일도 없다...!
  - 발송 상태 표시 방안 2가지
    1. 상태 컬럼 추가 (저자 선호, 2개 이상의 메시지 중계기가 있다면 방안2가 적합)
    2. 성공적으로 전송된 마지막 메시지 ID를 별도의 파일이나 테이블에 저장 후 다음번 대기 메시지 조회 조건으로 활용
  ```sql
    CREATE TABLE outbox (
        id              BIGINT AUTO_INCREMENT,
        message_id      VARCHAR(300),
        message_type    VARCHAR(300),
        payload         TEXT,
        status          VARCHAR(10) CHECK ( status IN ('WAITING','DONE','FAILED')),
        fail_count      INT DEFAULT 0,
        occured_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP(6),
        processed_at    TIMESTAMP DEFAULT NULL,
        failed_at       TIMESTAMP DEFAULT NULL,
        PRIMARY KEY (id)
    )
  ```
