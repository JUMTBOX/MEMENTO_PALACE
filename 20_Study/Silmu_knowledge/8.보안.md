## 8. 보안

**회원 식별자 관련 보안 문제점**
- 현재 요청이 로그인한 회원의 요청인지 확인하지 않음
- 회원 식별자가 로그인한 회원의 식별자인지 검증하지 않음
- 변경하기 전 암호를 검증하지 않음

### 인증(Authentication)과 인가(Authorization)

**인증과 토큰**
- 아이디와 암호를 입력하는 로그인은 인증의 한 형태
- 2단계 인증도 활용(Two-Factor Authentication)
- 생체정보 인증
- 토큰을 이용하여 사용자를 식별하기 위해서는 토큰과 사용자 간의 매핑 정보를 어딘가에 저장해야 한다.
  - 서버의 별도 저장소: 별도 저장소에 토큰과 사용자 식별 정보를 저장
    - `외부 저장소(DB, Redis)`: 토큰, 사용자 식별자, 생성 시간, 최근 사용 시간, 그 외 유효 시간, 클라이언트 버전 등 추가 데이터
    - `서버 메모리(Servlet Session)`: 메모리에 세션 객체를 저장, 서블릿 세션은 고유의 `세션ID`를 생성하는데 이 `세션ID`가 토큰에 해당한다
       <br/> 분산 환경에서는 고정 세션(Sticky Session)이 필요하다... 하여 세션 데이터를 DB나 Redis에 저장
  - `토큰(Json Web Token)`: 토큰 자체에 사용자 식별 정보를 저장
    - 토큰만 있다면 사용자 식별 가능
    - 외부 저장소에 토큰 데이터를 저장할 필요가 없으므로 서버 구조가 간단
    - 메모리에 토큰 데이터를 저장하지 않으므로 서버 수평 확장이 용이하다 (분산 환경 처리가 별도로 필요하지 않음)

**토큰 송수신**
- `쿠키`: 쿠키를 사용하여 전송
- `헤더(OAuth2.0 - Authorization 헤더)`: 특정 이름을 가지는 사용자 정의 헤더를 사용하여 전송
- URL 뒤에 붙이는 상남자 방식도 존재...

**토큰 보안**
- 토큰 유효 시간 제한
  - 생성 시점 기준 
  - 마지막 접근 시간 기준 (`접근마다 지속적으로 연장 / Servlet Session도 해당 방식 활용`)
  - 유효시간 check + `토큰을 생성할 때 접근한 클라이언트 IP와 실제 토큰을 전송한 클라이언트 IP가 같은지 비교`

**인가와 접근 제어 모델**
- 인증과 토큰은 사용자가 누군지 그리고 정상적으로 접근하는지 확인하는 역할이라면, 인가는 사용자가 요청한 기능을 실행할 권한이 있는지 확인하는 역할
- `접근 제어 모델`
  - > 역할 기반 접근 제어 (Role-Based Access Control, RBAC)
  - > 속성 기반 접근 제어 (Attribute-Based Access Control, ABAC) <br/>
    <br/> 
    ex )  사용자 IP 주소에 따른 특정 기능 접근 제어

**데이터 암호화**
- 단방향 암호화: 암호화한 데이터를 복호화할 수 없는 암호화 방식, 해시함수 이용 (SHA-256, MD5, BCrypt etc...)
    - 실제 암호화는 바이트 데이터를 기준으로 동작하기 때문에 `원본 문자열 -> byte[]` 변환, 암호화된 결과 저장을 위해서는 `byte[] -> 16진수 or Base64` 변환이 필요
    - 암호 + `Salt(임의값)`하여 해싱하면 RainbowTable 공격에도 안전
- 양방향 암호화: 암호화와 복호화가 모두 가능한 방식 (SSH protocol, Https), `AES`와 `RSA` 알고리즘이 존재
  - `대칭키 방식`: 암호화, 복호화 시 동일한 키 사용, 키 보안 중요
  - `비대칭키 방식`: 암호화시에는 공개키, 복호화시에는 개인키 사용

**HMAC(Hash-Based Message Authentication Code)**
**방화벽으로 필요한 트래픽만 허용하기**
- 물리적인 장비 방화벽
- 가상 방화벽(ex. Aws 보안 그룹)
- `인바운드 트래픽`: 외부에서 내부로 유입되는 것
- `아웃바운드 트래픽`: 내부에서 외부로 유출되는 것
